## 性能测量与限制

| 场景 | 本机结果 |
| --- | --- |
| 2,000 个会话的缓存列表读取 | 15 ms；未变 JSONL 重新解析 0 个，修改一个文件后仅重解析 1 个 |
| 同一规模首次后台建索引 | 约 11.9 秒；并行打包负载下主线程最大采样间隔约 67 ms |
| 不带额外资源的安装版 | 窗口约 2.2 秒出现，本地代理约 7.7 秒就绪（并行打包中） |
| 装齐资源，打包结束后独立启动 | 窗口约 1.1 秒出现，完整代理约 12.4 秒就绪 |
| 相同配置关闭后再开 | 窗口约 1.0 秒出现，完整代理约 11.3 秒就绪；会话保留 |

安装压缩与首次资源加载并发时曾测到约 37 秒。单独复测后降至上述范围；不能把并发负载作为唯一原因，也不能把窗口可见说成代理已经就绪。诊断显示扩展模块导入占用了明显时间。试用 Node 编译缓存未见明显改善，没有将其作为产品改动。

当前实现通过后台索引、会话列表分批、消息分段渲染、智能体目录缓存和运行中会话视图复用，减少历史增长及切换造成的卡顿。完整扩展冷启动仍需要时间，尚未做到瞬开；不能保证所有机器、扩展和会话体积都零延迟。

并行会话回归最终通过；此前在后台进程崩溃恢复后立刻新建会话的检查出现过一次失败，原样复测通过。该边界仍应在校内试用中关注，不据此宣称已经覆盖所有并发竞态。
