## 先整理安全的发布内容

开发目录不能整目录上传。历史中曾提交本地 Node 运行时二进制，仅补 `.gitignore` 不会把它们从历史中移除。

应在独立发布目录中，以确认的上游提交为基础整理学术派变更。原开发目录、未提交变更与原历史保留，不做强制重置或强推。发布前逐项核对候选文件及其历史：

- 纳入产品源码、构建配方、经过审查的锁文件、文档、Logo、截图与适用许可。
- 排除 `.artifacts`、私钥、账号配置、真实会话、个人输出、浏览器配置、依赖安装目录与运行时压缩包。
- 检查密钥、令牌、个人路径、二进制体积和不明确授权的第三方材料；报告中只记录文件和规则，不回显秘密值。
- 保留原始署名；第三方包适用各自许可。公开发布与内部使用不同，缺失许可或再分发条件应单独解决。
- 评审继承的 GitHub Actions：上游包含 npm 发布、R2 上传和贡献者自动关单规则。未完成衍生项目适配前，不启用它们，不推送会触发上游流程的版本标签。

## 下载链路还需要什么

现有签名资源清单指定 `packages/<sha256>.zip`。旧客户端禁止 HTTP 重定向，而 GitHub Release 使用平铺资产与 CDN 重定向，不能只更换 Base URL。本地新增的 `desktop/src/resource-fetch.cjs` 已处理这两种差异，保留原清单摘要与签名。

实现与发布验收必须同时覆盖：

1. 明确定义 Release 资产 URL 与现有签名清单的映射，不能默默丢失摘要或平台约束。
2. 允许经过审查的 HTTPS 重定向目的地；限制次数，不向跨域目的地转发凭据。
3. 保留 Range 续传、状态码和大小校验、SHA-256、签名及旧版本保留机制。
4. 主程序与智能体资源分别配置来源，按平台和架构验证。
5. 国内镜像只使用维护者明确配置的可信地址，与源站提供同一版本和摘要。以可达性和下载表现回退，不能仅靠 IP 所在地保证速度。
6. 在没有旧缓存的新配置中验证首次资源安装、中断恢复、坏包拒绝和版本升级，然后重新构建客户端 ZIP。

不要把签名私钥、GitHub 令牌或用户 JarodFund Key 放进客户端、仓库、截图或 Release。资源签名私钥应与公开托管服务分离。
